# Libratone Zipp / Zipp Mini OTA (FFAA) 解包与回打包工具

[English](README.en.md) | **简体中文**

解开 Libratone Zipp / Zipp Mini 音箱官方 OTA 固件包（`FFAA` 容器）的纯脚本工具，**Windows 拖放即用**，并且可以把解开的目录**原样打回**成设备能认的固件包。

不需要安装任何东西：`.bat` 已自带内嵌脚本，只依赖 Windows 自带的 PowerShell 和 .NET 4.5+。

```
FFAA-Unpack.bat   ← 把固件 zip 拖上去，当前目录自动多出一个同名文件夹
FFAA-Pack.bat     ← 把文件夹拖上去，生成 <文件夹名>_repack.zip
```

## 容器格式（逆向结果）

整个文件就是**一段明文文本头 + 一段被偏移混淆的 ZIP**：

```
"FFAA\n"
<BT 版本>   "\n"
<DSP 版本>  "\n"
<MCU 版本>  "\n"
<WiFi 版本> "\n"
<OTA 版本>  "\n"
"FFAA\n"
<payload>                     ← 混淆过的 ZIP
```

示意（字段真值随包而异，此处只表示结构）：

```
FFAA
BT_x.y.z
DSP_x.y.z
MCU_x.y.z
WIFI_x.y.z
879
FFAA
\x50\x4b\x03\x04 ...          ← 去掉混淆后就是标准 zip
```

**头部长度不是常量。** 它由五个版本字段的字符数决定：实测 `287` 是 42 字节，`621` / `879` 是 44 字节。所以代码里绝不能写死偏移，必须搜索第二个 `FFAA\n`（本工具搜索上限 4096 字节，用完即止）。

### 混淆算法

载荷（不含头部）逐字节变换，`i` 从载荷第一个字节起算 0：

```
加密：c[i] = (p[i] - (i & 15)) & 0xFF
解密：p[i] = (c[i] + (i & 15)) & 0xFF
```

就这一个公式，没有密钥、没有轮数、没有 S 盒。相当于一台"每 16 字节向下挪 1"的滚动滑梯。

### 还原出来的 ZIP

还原后是**标准的 Info-ZIP 风格压缩包**，条目元数据保留得很完整，这也是能逐字节打回的前提：

- extra 字段 `0x5455`（UTC 时间戳）+ `0x7875`（Unix UID/GID）
- central directory 里 `version made by = 0x031e`（Unix，PKZIP 3.0）
- 外部属性：普通文件 `0x81a40000`，目录 `0x41fd0010`
- 条目基本是 `deflate`，个别是 `store`

### 设备侧对应关系

包在设备上由 `system/bin/otahandler` 解析（它才是"官方解包器"），`system/bin/verdetect` 负责版本校验以防止降级。硬件是 Atmel SAMA5D3（Cortex-A5），Linux 3.10.0，用户态是 Android4SAM 4.4.2（bionic，没有 Dalvik、没有 APK）。知道了这些就能确认：这个格式从头到尾只是"文本头 + 线性偏移"，没有硬件相关加密。

## 我是怎么解出来的

记录一下思路，因为这套方法对别的"看起来加密了"的固件包同样好用。

**1. 先看头。** 文件开头是明文 `FFAA`，五个可读版本号，再一个 `FFAA`。厂商连头部都没加密，说明混淆只作用在载荷上，而且大概率是**可逆的轻量变换**，不是真加密。

**2. 排除已知容器。** 尾部没有 `PK\x05\x06`（EOCD），排除正常 ZIP；没有 `hsqs`，排除 squashfs；没有 `UBI#`，排除 UBI。载荷熵接近 8 bit/byte，排除明文。

**3. 打差分找指纹。** 这一步是破局点。对 `c[i]` 做不同 lag 的差值统计，取众数：

```
lag = 1  →  众数 -1
lag = 2  →  众数 -2
lag = 4  →  众数 -4
```

差值众数恰好等于 `-lag`，这是**线性递减项的指纹**：`p[i] - p[i-k]` 原本应该接近 0，现在整体偏了 `-k`。几乎可以断定 `c[i] = p[i] - f(i)`，且 `f(i+k) - f(i) = k`。

**4. 找周期。** 对齐到 16 字节边界后，同一个相位上出现了 180 次完全相同的 16 字节块，其众数序列是：

```
00 ff fe fd fc fb fa f9 f8 f7 f6 f5 f4 f3 f2 f1
```

这正是 `-(i & 15) & 0xFF`。而且这种"全零明文"的大块在 ZIP 里非常常见（未压缩的零填充、对齐区），所以能统计出来。周期 = 16，掩码 = `i & 15`。

**5. 验证假说。** 取 `p[i] = (c[i] + (i & 15)) & 0xFF` 重算，第一个字节立刻变成 `0x50 0x4B 0x03 0x04`，用 Python `zipfile` 逐条 CRC 校验全过。

**6. 交叉验证"相位起点"。** 换一个更旧的包（头部 42 字节，比新包短 2 字节）再解一次，**同一公式直接成立**，不需要平移补偿。说明相位是从载荷第一个字节起算的，与头部长度无关——这一步顺便证明了它不是"按整文件偏移"做的，也是它能通用于所有包的原因。

## 为什么这不是"版本匹配"

我把代码里所有可能藏着版本假设的地方都检查了一遍，实际只存在两个数字：

- `4096` —— 搜索头部结束标记时的上限，纯粹是防御性边界
- `15` —— 掩码

**没有任何版本表、机型表、哈希白名单或分支判断。** 为了证明这一点，我构造了四种**现实中不存在**的头部（7 字节 / 54 字节 / 37 字节 / 39 字节，版本字段位数各不相同），塞进同一份载荷，全部能被正确识别并逐字节还原。

所以结论是：**这是通用格式代码**。只要包符合"`FFAA\n` … `FFAA\n` + 线性偏移载荷"这个结构就能解，包括尚未发布的版本。目前只在 287 / 621 / 879 上实测过，是因为只拿到了这三个包，不是代码只能处理这三个。

## 解包用法

### 方式一：拖放（推荐）

1. 把固件包（如 `xxx_879.zip`）拖到 `FFAA-Unpack.bat` 图标上
2. 当前目录出现同名文件夹 `xxx_879\`，解开的内容都在里面
3. 也可以双击运行后把路径粘进去，支持一次贴多个

### 方式二：命令行

```bat
FFAA-Unpack.bat "D:\fw\zipp_879.zip"

REM 或者直接用 PowerShell 版，参数一致
powershell -NoProfile -ExecutionPolicy Bypass -File ffaa_unpack.ps1 "D:\fw\zipp_879.zip"
```

### 输出结构

```
D:\fw\
├─ zipp_879.zip              ← 原始包，不动它
└─ zipp_879\                 ← 新建
   ├─ ffaa_header.txt        ← 关键：原样保存的容器头
   ├─ mcu_app.bin
   ├─ dsp_app.bin
   ├─ system_ubifs
   └─ ...
```

- 目标文件夹已存在时自动改名 `zipp_879_1`，**绝不覆盖**
- 普通 ZIP（没有 FFAA 头）也能直接丢进来，会跳过剥离步骤
- `ffaa_header.txt` 是给回打包用的，存的是那 42/44 字节的原始头部（含换行、一个字节都不差）。**不要删它**，删了之后打包只能靠猜版本号

### 跨平台解码

```bash
python3 tools/ffaa_decode.py firmware.zip            # 解码 + 解压
python3 tools/ffaa_decode.py firmware.zip --info     # 只看头部字段
python3 tools/ffaa_decode.py firmware.zip -o out.zip # 只解码不解压
```

## 打包用法

### 方式一：拖放

1. 确保**原始 zip 仍和解包出的文件夹放在同一层目录**（这是拿到真实头部的唯一可靠来源）
2. 改文件、加文件、删文件都行
3. 把文件夹拖到 `FFAA-Pack.bat` 上
4. 生成 `zipp_879_repack.zip`（同名已存在则加 `_1` 后缀，不覆盖原包）

### 方式二：命令行

```bat
ffaa_pack.ps1 <文件夹> [<文件夹> ...] [-Template <zip>] [-Version <号>] [-Out <输出>] [-Plain] [-NoVerify]
```

| 参数 | 作用 |
| --- | --- |
| `文件夹` | 要打包的目录，可给多个，会依次处理 |
| `-Template <zip>` | 显式指定模板包；不写就自动找同级的 `<文件夹名>.zip` |
| `-Version <号>` | 覆盖 OTA 版本号字段（用于伪造/回退测试） |
| `-Out <路径>` | 指定输出文件或输出目录；默认 `<文件夹>_repack.zip` |
| `-Plain` | 不加 FFAA 头，输出**普通 ZIP**（用于对比排查） |
| `-NoVerify` | 跳过打包后的反向解码校验（不推荐） |

### 打回时到底做了什么

这是整个工具里最容易被写错的部分。**不能用普通 zip 库直接压缩**，因为 Info-ZIP 的 deflate 实现和 zlib 的默认输出不一致（我试过 level 0~9、各种 memLevel 和 strategy，都无法复现原始字节流），所以采用**模板复用**：

1. **找模板** —— 优先级：`-Template` 指定 → 同级的 `<文件夹名>.zip` → 文件夹里的 `ffaa_header.txt` → 只能靠猜（见限制）
2. **比对条目** —— 逐条算 CRC 和大小，与模板 central directory 对照，分成四类：未变 / 修改 / 新增 / 删除
3. **未变条目** —— **原封不动复制**原始 local header、extra 字段（`0x5455` / `0x7875`）和压缩后的字节流，只重算它在新区块里的偏移量 `lho`
4. **修改过的条目** —— 重新 deflate + 重算 CRC，并沿用原来的 extra 字段风格
5. **新增条目** —— 按 Info-ZIP 规则构造：extra = `0x5455`（mtime）+ `0x7875`（uid/gid），`vma` 按类型区分（文件 `0x81a40000` / 目录 `0x41fd0010`）
6. **重排** —— 先写 local header + 数据，再写 central directory 和 EOCD，记录每个条目的新偏移
7. **加头** —— 把 `ffaa_header.txt` 的内容原样放回去，再对整段载荷做**反向混淆**（`- (i & 15)`）
8. **反向校验** —— 把产物再解一次，检查条目数、逐个 inflate、逐个 CRC；任何一步不对就报错并且不落盘

因为第 3 步是原样复制，**什么都不改的包打回去和原包 MD5 完全一致**。这也是判断"我的改动有没有破坏格式"的最好办法：先原样回环一次，比对 MD5，通过之后再动内容。

### 输出示例

```
  [*] zipp_879
       template  : zipp_879.zip
       header    : 1.2.3 | 4.5.6 | 0.9.8 | 1.0.1 | 879
       entries   : 8   same 7, changed 1, added 0, removed 0
       verify    : OK  (decoded again, all CRCs match)
  [OK] zipp_879_repack.zip   26,462,146 bytes
```

`same` 是原样复制的，`changed` 是重新压缩的，`added` / `removed` 是增删的。看到 `same` 数量符合预期，就说明模板匹配没问题。

## 限制与已知问题

- **只支持 ZIP 载荷。** 如果遇到载荷不是 `PK\x03\x04` 的变体，工具会明确报"unknown container variant"而不是吐出垃圾数据。
- **改动过的条目压缩字节与原厂不同。** 内容、CRC、大小都对，但 deflate 字节流无法逐位复现 Info-ZIP。如果设备在刷机时严格比对整包签名（目前没发现，只剩 `verdetect` 校版本号），这一步会卡住。
- **找不到模板时会告警。** 此时智能读出 MCU 版本，BT/DSP/WiFi 填 `0.0.0`，头部长度也随之变化。这样打出来的包**很可能被设备拒绝**，仅适合格式研究。
- **`verdetect` 会校验版本号防止降级。** 用 `-Version` 改小版本号理论上会被拒。**我没有在真机上刷过任何自制包**，以下载来的官方包为基准做回环验证是安全的，真刷机风险自负。
- **需要 .NET Framework 4.5+**（Windows 8 / Server 2012 及以上自带）。
- **`.bat` 依赖 `certutil.exe`** 把内嵌的 PowerShell 脚本还原到临时目录。如果 `certutil` 被策略禁用，直接跑对应的 `.ps1` 即可。
- 解包 26 MB 的包约 2~3 秒，主要花在逐条 CRC 校验上。

## FAQ

**Q：为什么解出来的东西看着像一堆二进制？**
主体是 `system_ubifs`，那是 UBIFS 镜像，不是 tar。用 `ubireader_extract_files`（`pip install ubi_reader`）可以挂出来看完整文件系统。`mcu_app.bin` / `dsp_app.bin` 是裸固件，给对应 MCU / DSP 用的。

**Q：能刷吗？**
不知道，我没试过。除了容器格式，设备还有 `verdetect` 做版本校验，而且刷坏了需要能进恢复模式才能救。本工具定位是分析与研究，不是刷机工具。

**Q：为什么打包不直接用 Python 的 `zipfile` 重写一遍？**
因为那样输出的整包字节会和原厂不同（deflate 实现差异 + extra 字段差异），无法通过 MD5 回环比对，也就无法证明"除了我改的地方，其它都没动"。模板复用策略能给你这个保证。

**Q：`ffaa_header.txt` 被我删了怎么办？**
把原始 zip 放回文件夹旁边，脚本会自动从里面重新读头部。两者都没有就只能靠猜，会告警。

**Q：中间版本（554 / 588 / 665 / ...）能解吗？**
格式上应该可以（见"为什么这不是版本匹配"），但我手上没有这些包。它们的下载地址只存在于厂商云端数据库，CDN 上已无镜像。
